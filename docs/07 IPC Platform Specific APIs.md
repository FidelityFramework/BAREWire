# Platform-Specific APIs in BAREWire

## 1. The Cross-Platform Question

BAREWire's IPC design ([06 IPC Integration](./06%20IPC%20Integration.md)) specifies shared memory, named pipes, and message queues over operating-system primitives that differ per platform. This memo states how platform specificity is resolved in the Fidelity Framework — **at compile time, in source, with nothing selected at runtime** — and where the seam sits: **the OS-primitive binding layer belongs to Fidelity.Platform, not to BAREWire.** BAREWire's remit at this seam is the same as everywhere else: the typed contract and the layout — schemas, descriptors, and typed regions and views over whatever handle or mapped region the platform tree provides. BAREWire consumes the platform surface; it never binds it.

There is no provider interface, no runtime registry, and no platform detection. A native binary does not discover its platform; it is compiled for one. The target is declared in the project (`.fidproj`), the per-target platform source tree supplies the bindings, and the compiler resolves every platform call to a direct native call before emission.

## 2. The Resolution Chain

```
.fidproj target declaration
        │
        ▼
Fidelity.Platform per-target source tree        (e.g. CPU/Linux/x86_64/)
        │   Console.clef, Syscalls.clef, ...    platform API surface in Clef
        ▼
CCS platform intrinsics                         (Sys.read, Sys.write, ...)
        │   typed in the native type universe
        ▼
Composer platform-binding resolution            (a coeffect, computed once
        │   before emission)                     per compilation
        ▼
Alex emission: direct calls                     (func.call @write, ...)
```

Each layer is source or compiler analysis; none is runtime machinery — and BAREWire appears nowhere in this chain, which is the point: everything BAREWire adds sits above it, as contract and layout. The platform surface is ordinary Clef code in the per-target tree — `Console.write` calls `Sys.write STDOUT s`, and the binding-resolution coeffect maps the intrinsic to the target symbol and calling convention for the declared platform. The emitted program contains direct calls with the memref-to-pointer/length conversion at the boundary; there is no marshaling layer because there is no runtime type system to marshal across.

```fsharp
// Fidelity.Platform/CPU/Linux/x86_64/Console.clef — the platform surface is source
[<Literal>]
let STDIN = 0

let write (s: string) : unit =
    let _ = Sys.write STDOUT s
    ()
```

For platform APIs that live in shared libraries rather than the syscall interface (the Win32 surface, vendor runtimes), the declarations are generated by **Farscape** from the actual C/C++ headers via clang — real ABI, not header surface — and linked directly or loaded dynamically (`dlopen`/`dlsym`, itself a bound platform call). The same chain applies: declared surface, compile-time resolution, direct calls.

## 3. Per-Target Binding Surfaces for IPC

The IPC design rests on these OS primitives per target. The facts in these tables are stable properties of the operating systems; the per-target **Fidelity.Platform** trees are where they become typed Clef surfaces — none of these bindings live in BAREWire.

**Linux / POSIX** (direct syscalls and libc):

| primitive | calls |
| --- | --- |
| Shared memory | `shm_open`, `ftruncate`, `mmap`, `munmap`, `close` |
| Named pipes | `mkfifo`, `open`, `fcntl` (O_NONBLOCK), `close` |
| Local sockets | `socket`, `bind`, `listen`, `accept`, `connect` (AF_UNIX) |

**Windows** (kernel32 via Farscape-generated declarations):

| primitive | calls |
| --- | --- |
| Shared memory | `CreateFileMapping`, `MapViewOfFile`, `UnmapViewOfFile`, `CloseHandle` |
| Named pipes | `CreateNamedPipe`, `ConnectNamedPipe`, `CloseHandle` |

A shared-memory create on the Linux tree, in the shape the platform surface takes:

```fsharp
/// Fidelity.Platform (Linux tree): shared memory region creation
let createSharedMemory (name: string) (size: int<bytes>) : Result<SharedHandle, IpcError> =
    let fd = Sys.shm_open name (O_RDWR ||| O_CREAT) 0o666
    if fd < 0 then Error (ShmOpenFailed name)
    else
        match Sys.ftruncate fd (int64 size) with
        | e when e < 0 ->
            Sys.close fd |> ignore
            Error (SizeFailed (name, size))
        | _ ->
            let addr = Sys.mmap 0n (unativeint size) (PROT_READ ||| PROT_WRITE) MAP_SHARED fd 0L
            if addr = MAP_FAILED then
                Sys.close fd |> ignore
                Error (MapFailed name)
            else
                Ok { Fd = fd; Base = addr; Size = size }
```

BAREWire's IPC modules ([06](./06%20IPC%20Integration.md)) sit on these surfaces: the schema and view layers are platform-independent, and the binding layer that differs per target is Fidelity.Platform's. The layout the two processes agree on is the BAREWire schema — the typed contract of [Substrate_Formalism](./Substrate_Formalism.md) — not the transport.

## 4. Resource Management

Lifetime is deterministic memory management, not disposal patterns. Handles and mapped regions are plain values; their release is scope-driven under the framework's coeffect discipline — stack, arena, or actor scope per the escape classification (see the DTS+DMM paper and [Arena_Design](./Arena_Design.md)). A mapped region's lifetime bound is a compile-time property of the value, and releasing it (`munmap`/`close`, `UnmapViewOfFile`/`CloseHandle`) is emitted at the scope boundary the coeffect determines. There are no finalizers and no reference-counted wrappers around OS handles.

## 5. Boundaries Without an Operating System

Two target classes have no OS IPC to bind, and neither gets a simulated provider:

- **The JavaScript/WREN boundary.** Type erasure, not process isolation, is the boundary. BAREWire's encoding modules carry the typed contract across it — case structure and dimensional annotations preserved by construction — with the transport being whatever the web context provides (WebSocket IPC on the WREN stack). See [Substrate_Formalism](./Substrate_Formalism.md) on the erasure boundary.
- **FPGA and freestanding targets.** No processes, so no IPC in the OS sense: communication is on-chip queues, DMA regions, and wire transports, declared through BAREWire descriptors the same way peripherals are ([08 Hardware Descriptors](./08%20Hardware%20Descriptors.md), [11 Platform Description](./11%20Platform%20Description.md)). The contract layer is identical; the primitives beneath it are the target's own.

## 6. The Proof Surface

Because the platform surface is source and the bindings resolve at compile time, every capacity, layout, and contract in the IPC path is visible to the compiler's proof-obligation generation: buffer capacities and framing come from declared schemas, shared-region layouts from BAREWire descriptors, and the far side of each boundary is a declared trusted-base assumption. Obligations are stated against the declarations and discharged during compilation; see [11 Platform Description](./11%20Platform%20Description.md) for the declared-then-directed-then-confirmed loop this feeds.

## 7. Status

The IPC modules themselves are design ([Implementation Status](./Implementation%20Status.md)): no `IPC/` source exists yet. The binding pattern is live in the Linux x86_64 Fidelity.Platform tree (console and syscall surfaces), and the division of labor is fixed: Fidelity.Platform binds the primitives per target; BAREWire supplies the contract and layout over them — per-target Clef source, compile-time resolution, direct calls, deterministic lifetimes, schemas as the cross-process contract.
